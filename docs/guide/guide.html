0 The big picture

Support agents receive many tickets. This system helps them in two ways:

  1. Chat (RAG): ask a question, get an answer built only from help-centre articles, with clickable sources.
  2. Triage agent + approvals: the AI reads a ticket and proposes category, priority and a reply. A human approves, edits or rejects. Only approved actions change the ticket.

Everything is measured (traces in Langfuse), every setting lives in .env, and every decision is written to an audit log that nobody can change.

1.2 Configuration and secrets (.env → Zod → config)

Step by step
  1. 1.2.1 Search upward from the current folder for .env (works from any package). → config.ts → findEnvFile()
  2. 1.2.2 Load it into the process; variables already set (CI, Docker) win. → process.loadEnvFile(envFile)
  3. 1.2.3 Treat blank values (KEY=) as "not set". → blankToUndefined()
  4. 1.2.4 Validate every variable (numbers, URLs, enums, booleans). → envSchema.safeParse(process.env)
  5. 1.2.5 Stop with a readable error if anything is wrong. → throw new Error(prettifyError)
  6. 1.2.6 Export one frozen, typed object; everyone imports it. → export const config / import { config } from '@sta/shared'
  • Every setting and secret in one place; nothing hardcoded.
  • Fail fast: a wrong value stops the app at startup with a readable message.
  • Typed: config.llm.temperature is a number, config.features.agentEnabled a boolean.

2 The database (simple explanation)

One PostgreSQL database (support) holds everything. There are 6 tables in two groups:

  • Knowledge base (RAG): documents → chunks
  • Triage + approvals: tickets → agent_runs → proposed_actions, plus audit_log

2.1 Tables and relationships

How to read it: ||--o{ means "one to many". One document has many chunks. One ticket has many agent runs. One run proposes many actions. PK = primary key (unique id), FK = foreign key (points to another table), UK = unique.

Key idea: audit_log.ticket_id has no foreign key: if a ticket is deleted, its runs and proposals are deleted (cascade), but its audit history must stay.

2.2 What each table is for

TableOne row = …Important columnsRules
documentsone help article (file)source, content_hash, metadata.fingerprintsource unique (re-ingest updates)
chunksone piece of an articlecontent, embedding vector(1024)cascade delete; HNSW cosine index
ticketsone support ticketsubject, description, category, priorityno PII columns; category/priority set only by approvals
agent_runsone triage run on a ticketstatus, model, prompt_version, trace_id, resultrunning → completed | failed
proposed_actionsone thing the agent wants to dotype, payload, rationale, status, expires_atpending → approved → executed | failed; rejected; expired
audit_logone eventactor, event, details, ticket_idappend-only (trigger blocks UPDATE/DELETE)

2.5 Useful SQL to explore

-- chunks per article
select d.title, count(*) from chunks c join documents d on d.id = c.document_id group by 1;

-- proposals waiting for a human
select t.external_id, a.type, a.status, a.rationale
from proposed_actions a join tickets t on t.id = a.ticket_id where a.status = 'pending';

-- the full history of one ticket
select occurred_at, actor, event, details from audit_log
where ticket_id = (select id from tickets where external_id = 'SAMPLE-003') order by id;

-- try to change history (fails on purpose)
update audit_log set event = 'x';   -- ERROR: audit_log is append-only

4.3 Grounded answers: threshold, prompt, citations

Step by step
  1. 4.3.1 Start a trace "rag-chat" (chain observation). → answer.ts → answerQuestion()
  2. 4.3.2 Embed the question (cache first) and fetch the 8 nearest chunks. → retriever.ts → retrieve() · embedQuery() · searchChunks()
  3. 4.3.3 Keep chunks with distance ≤ 0.70; none left → "not found", no LLM call. → config.rag.maxDistance
  4. 4.3.4 Keep the best 4 and number them [1]–[4]. → reranker.ts → rerank()
  5. 4.3.5 Build the prompt: rules (answer-v2) + <sources> blocks + question. → answer.prompt.ts → buildAnswerUserMessage()
  6. 4.3.6 Call the LLM through the traced provider. → getChatProvider().chat({ tier: 'chat' })
  7. 4.3.7 Normalise citations, detect "not found", map [n] to sources. → citations.ts → normaliseCitations() · citedIds()
  8. 4.3.8 Return answer, citations, sources, usage, timings, traceUrl. → ChatResponse

5.2 The triage workflow

Step by step
  1. 5.2.1 Load the ticket by external id or uuid (404 if missing). → triage.agent.ts → loadTicket()
  2. 5.2.2 Record the run first (status running, prompt version, trace id). → insert agent_runs
  3. 5.2.3 Retrieve help-centre sources for subject + description. → retrieve(triageQuery(ticket))
  4. 5.2.4 Ask the LLM for JSON; validate with Zod; repair once with the errors. → suggest() · TriageSuggestionSchema
  5. 5.2.5 Apply guards: no ungrounded reply, consistent escalation. → applyGuards()

  7. 5.2.7 One transaction: expire older pending proposals, insert new pending ones, audit, run completed. → db.transaction(...)
  8. 5.2.8 If anything fails: run failed + audit run.failed. → catch → agent_runs.status = failed

5.3 Approvals: the safety rules

Step by step
  1. 5.3.1 Before listing: expire overdue pending proposals (audited). → approval.service.ts → expireOverdue()
  2. 5.3.2 Atomic claim: set approved only if still pending and not expired. → UPDATE … WHERE status = 'pending' AND expires_at > now()
  3. 5.3.3 No row claimed → explain why (404, 409 expired, 409 already decided). → notDecidable()
  4. 5.3.4 Validate the (possibly edited) payload; invalid → 400 and rollback. → ActionPayloadSchemas[type].safeParse()
  5. 5.3.5 Audit the approval (edited? original payload). → audit action.approved
  6. 5.3.6 Execute in a savepoint: update the ticket; success → executed, error → failed. → applyAction()
  7. 5.3.7 Return the item and the ticket after the change. → loadItems()

7.2 Top 10 lessons

  1. Check your data before trusting metrics (labels were random).
  2. Most "model errors" are specification errors (overlapping category definitions).
  3. Don't tune and test on the same data (overfitting).
  4. Depend on interfaces, not vendors (switched both vendors in one step).
  5. Read error codes: billing ≠ rate limit ≠ bad key.
  6. Choose thresholds from measurements (0.70 from real distances).
  7. Test with the real model: output formats drift (【1】).
  8. Put must-hold rules in the database (append-only trigger, atomic claim).
  9. LLM output is untrusted input for the UI (no raw HTML).
  10. Verify where you are connected / what is served (port clash, stale dev bundle).
