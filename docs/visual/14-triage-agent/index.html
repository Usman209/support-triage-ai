Step 14 · Task 4.3

Triage agent: proposes, never acts

One ticket in, a structured suggestion out: category, priority, a grounded reply, maybe an escalation. Saved as pending proposals. The ticket doesn't change until a human approves.

2. Workflow vs agent loop (why we chose a workflow)

Workflow (chosen)

Steps known in advance. Code controls the flow, the LLM fills the values. Cheaper, faster, predictable, easy to evaluate.

Agent loop

The model chooses tools step by step. Worth it when the path depends on what it finds. More tokens, harder to test and control.

3. What one run produces (SAMPLE-003, "charged twice")

Proposal Payload Rationale Status
set_category billing_inquiry duplicate charge pending
set_priority high "charged wrongly" pending
draft_reply "… 3–5 business days [1] … refund within 2 business days [1] …" grounded in sources pending
add_internal_note "verify order number …" for colleagues pending

The ticket's own category is still null: nothing is applied until approval.

Problems and fixes

Symptom"Charged twice" → refund_request
CauseOverlapping definitions (money back vs charges)
Fixtriage-v2: charges are billing, even if refunded
Lesson: most "model errors" are specification errors.
SymptomRisk of overfitting to 12 tickets
CauseSame set to find and fix problems
FixOnly general rules; held-out set in task 7
Lesson: never tune and test on the same data.
SymptomLater calls 7–13 s
CauseGroq free-tier tokens-per-minute limit
FixSDK retries; pauses between calls
Lesson: rate limits shape batch jobs.
Interview line: "Triage is a workflow, not a free agent: the LLM returns a Zod-validated suggestion with one self-repair attempt, code turns it into proposals of allow-listed types, and everything is stored as pending with rationale, expiry and audit. A small eval took the prompt from 83% to 100% on our sample by fixing overlapping definitions, and we know that number is optimistic."
